# Asset caching

Why the `headers` block in `vercel.json` looks the way it does. (JSON has no
comments, and Vercel rejects unknown keys like `"//"` in a headers entry, so the
rationale lives here.)

## The problem it fixes

Vercel's default for static output is:

```
cache-control: public, max-age=0, must-revalidate
```

That was being served for **everything**, including content-hashed build output
like `index-BcxBaChj.js`. Every visitor revalidated every asset on every page
view — roughly 35 conditional requests per page load that should have been zero.
At the site's traffic that is a large amount of latency and egress bought for
nothing.

## The rules

| Pattern | Policy | Why |
|---|---|---|
| `/assets/*.(js\|css)` | `max-age=31536000, immutable` | Vite content-hashes these filenames. A change always produces a new URL, so the old one can be cached forever and never revalidated. |
| `/assets/**` images | `max-age=604800` + `stale-while-revalidate=2592000` | These come from `public/` and have **stable** filenames, so they are deliberately *not* immutable. A week of hard caching, then a month where a stale copy serves instantly while the new one downloads in the background. |
| `/assets/docs/**` | `max-age=86400` + SWR | The sponsorship packet is revised more often than photos. |

`index.html` is deliberately **absent** from the list. It keeps Vercel's default
`max-age=0, must-revalidate` so a new deploy is picked up immediately — this is
what makes the `immutable` policy on hashed assets safe.

The image rules intentionally overlap (`/assets/photos/(.*)` also matches the
extension rule above it). Both carry identical values, so the result is the same
whichever one Vercel applies.

## Replacing an image

Because image filenames are stable and cached for up to a week, replacing a photo
in place can take that long to reach visitors who already have it. To force it
immediately, save it under a new filename and update the reference.

## Related

Images are served as `.webp`, generated by `scripts/optimize-images.py`. The
original `.jpg`/`.png` files are kept as a fallback so a missed reference
degrades to a larger image rather than breaking.
